# Ghost Booth — Full Rebuild Specification

This document specifies Ghost Booth **as it is actually built today**, not the
aspirational plan in `CLAUDE.md`. It is meant to let someone (or a fresh
Claude session with zero other context) regenerate this exact codebase,
including every bug fix, revert, and hardware-driven design decision that
happened along the way. Where `CLAUDE.md` describes something that was never
built, tried-and-reverted, or built differently than planned, this document
says so explicitly and describes the real thing.

Source of truth this was written from: `CLAUDE.md` (original spec),
`PROJECT_LOG.md` (append-only decision log, ~1,540 lines), `package.json`,
every file under `src/`, `public/`, `.github/workflows/deploy.yml`, and
`vite.config.ts`.

---

## 1. Overview

Ghost Booth is a full-screen, unattended Halloween photobooth **web app**
(TypeScript + React + Vite), designed to run installed-to-home-screen in
Safari on an iPad mounted in **portrait** orientation, paired with a
Bluetooth **Kodak Mini 2 Retro** photo printer. A guest taps to start, sees a
live mirrored camera preview, triggers a 3-2-1-BOO countdown, and gets back a
caricatured "goofy" version of their photo (via real-time face-landmark mesh
warping, not generative AI) with an optional ghostly cameo image composited
in, an optional whole-photo color-grade ("Filters" — horror-movie-style
grades or poster tints), and an optional random adult-Halloween-party
caption. Every guest pick recomposes the photo live via Canvas2D/WebGL2 —
nothing is generated by a server; there is no backend at all. The finished
photo is hardware-cropped to the printer's 2:3 portrait shape and handed off
through the iOS share sheet (a custom "Print to Kodak" Shortcut, built by the
operator, saves it to an album and opens the Kodak app automatically — direct
Bluetooth printing from Safari is not possible on this platform, confirmed on
real hardware). The whole app runs offline-capable via a hand-written service
worker, and is deployed to GitHub Pages via GitHub Actions.

## 4. The booth state machine

Single authoritative reducer, `src/state/BoothStateMachine.ts` — no scattered
booleans (`CLAUDE.md` section 4 is honored exactly as specified).

```ts
export type BoothState =
  | "attract" | "camera" | "ready" | "countdown" | "capturing"
  | "processing" | "result" | "printing" | "printComplete" | "error";

export interface BoothContext {
  state: BoothState;
  error?: string;
  hasFinishedPhoto: boolean;
  /** Where RETRY should return to; set whenever we transition into "error". */
  retryTarget: BoothState;
}
```

Events: `GUEST_APPROACHED`, `CAMERA_READY`, `CAMERA_ERROR{message}`,
`START_COUNTDOWN`, `COUNTDOWN_COMPLETE`, `FRAME_CAPTURED`,
`CAPTURE_ERROR{message}`, `PROCESSING_COMPLETE`, `PROCESSING_FAILED{message}`,
`PRINT_REQUESTED`, `DONE`, `RETAKE`, `PRINT_SUCCESS`, `PRINT_FAILED{message}`,
`RESET`, `RETRY`, `IDLE_TIMEOUT`.

Notable transition details:
- `error` state carries `retryTarget`. A camera/capture error's `retryTarget`
  is `"camera"`; a print failure's is `"printing"`. `App.tsx`'s `renderScreen`
  special-cases `retryTarget === "printing"` to route through
  `PrintingScreen`'s failure UI (TRY AGAIN/SAVE PHOTO/CONTINUE WITHOUT
  PRINTING) instead of the generic single-button error screen — this was a
  real P0 bug (see §17) that made the "never discard the finished photo"
  requirement unreachable in practice.
- `PRINT_FAILED` keeps `hasFinishedPhoto: true` — printing errors never
  discard the photo.
- `IDLE_TIMEOUT` is a global override handled from every state via a
  fallthrough at the end of the reducer, resetting to `initialBoothContext`.
- Unknown/invalid transitions are no-ops (context returned unchanged), never
  thrown.

`AppState` (`src/app/AppState.ts`) wraps this in a second, tiny reducer that
also carries `settings: BoothSettings`:

```ts
export interface AppState { booth: BoothContext; settings: BoothSettings; }
export type AppAction =
  | { kind: "booth"; event: BoothEvent }
  | { kind: "settings"; patch: Partial<BoothSettings> }
  | { kind: "settings/reset" };
```

`CameraScreen` stays mounted across `camera`/`ready`/`countdown`/`capturing`
(rendered by `renderScreen` for all four), with `Countdown`/`ProcessingScreen`
layered on top as an `overlay` prop — unmounting `CameraScreen` would stop the
`MediaStream`, which previously broke capture.

## 6. Camera & capture pipeline

### 6.1 getUserMedia constraints — portrait, not landscape

```ts
function defaultCameraConstraints(): MediaStreamConstraints {
  return {
    video: { facingMode: "user", width: { ideal: 1080 }, height: { ideal: 1920 } },
    audio: false,
  };
}
```

**This is the opposite of `CLAUDE.md`'s literal example** (`{ ideal: 1920 }`
width × `{ ideal: 1080 }` height). The booth is physically mounted
**portrait** (operator-confirmed) and the Kodak Mini 2 Retro only ever
outputs portrait 2×3 prints. `getUserMedia` width/height constraints are a
literal pixel-dimension hint, not orientation metadata — they do not
auto-swap for device orientation — so requesting landscape `ideal` dimensions
while mounted portrait biased Safari toward handing back a landscape-shaped
stream, which then silently disagreed with the printer's fixed portrait
paper. Requesting portrait `ideal` dimensions makes every later stage
(composition, caption placement, print crop) already work in portrait
without a rotation step in the common case.

### 6.2 `CameraManager` (`camera/CameraManager.ts`)

```ts
export interface CameraManager {
  start(): Promise<void>;
  stop(): void;
  getStream(): MediaStream | null;
  captureFrame(): Promise<ImageBitmap>;
}
```

`GetUserMediaCameraManager` implements this with an offscreen `<video>`
element used purely to decode the stream (never a repeated low-quality
screenshot of the visible preview — `captureFrame()` calls
`createImageBitmap(this.videoEl)` at full native resolution). `CameraError`
wraps `DOMException` names into a typed `kind`:
`"permission-denied" | "not-found" | "in-use" | "unsupported" | "unknown"`.

### 6.3 `CameraPreview.tsx`

Pure presentation: attaches the `MediaStream` to a `<video>`, mirrored via
CSS `transform: scaleX(-1)` for a natural selfie feel. Never touches capture.

### 6.4 `captureMasterFrame()` (`camera/CaptureService.ts`) — the real pipeline

```
raw = camera.captureFrame()
  ↓
maybeRotateToPortrait(raw)         // iOS rotation-quirk fix, see 6.5
  ↓ (only if landscape frame + portrait viewport)
rotated (or raw unchanged)
  ↓
drawNormalized(ctx, rotated, w, h, mirror=true)   // un-mirror
  ↓
master ImageBitmap                 // final: correctly oriented, un-mirrored
```

Every intermediate is `.close()`d once superseded (P0 bitmap-lifecycle fix,
see §17).

### 6.5 The iOS Safari rotation quirk (critical, hard-won fix)

Even after (6.1)'s portrait `ideal` request and even with `computeCoverCropRect`
forcing a portrait print crop, guests still got landscape photos with the
caption cut off. Root cause, found last: **iOS Safari's live `<video>`
preview displays a getUserMedia stream correctly rotated to match device
orientation via an internal transform, but a canvas/`ImageBitmap` capture of
that same stream does NOT inherit that transform** — it grabs the raw
landscape sensor buffer. `captureMasterFrame` detects this per-capture and
corrects it:

```ts
function maybeRotateToPortrait(raw: ImageBitmap, rotateCounterClockwise: boolean): ImageBitmap {
  const viewportIsPortrait = window.innerHeight >= window.innerWidth;
  const frameIsLandscape = raw.width > raw.height;
  if (!viewportIsPortrait || !frameIsLandscape) return raw; // no-op elsewhere
  const canvas = new OffscreenCanvas(raw.height, raw.width); // dims swapped
  const ctx = canvas.getContext("2d")!;
  drawRotated90(ctx, raw, raw.width, raw.height, !rotateCounterClockwise);
  return canvas.transferToImageBitmap();
}
```

`utils/orientation.ts`'s `drawRotated90` rotates via `ctx.translate` +
`ctx.rotate(±Math.PI/2)`. There is **no way to know from code** which
direction (CW/CCW) the front camera sensor is physically offset relative to
device housing — that only shows up on the real hardware — so
`settings.rotateCaptureCounterClockwise` (Operator Panel → Camera section) is
an escape hatch the operator flips on-site if a TEST CAPTURE comes back
upside-down/sideways, rather than needing a new deploy.

### 6.6 `computeCoverCropRect` / print-time crop (`printing/PrintLayout.ts`)

Runs once, immediately before handing the composed photo to a printer
adapter — never touches what's displayed on the result screen.

```ts
export type PrintLayout = "2x3" | "4x6" | "square" | "2x6strip";
const FORCE_PORTRAIT_LAYOUTS = new Set<PrintLayout>(["2x3", "4x6"]);
const SHORT_TO_LONG_RATIO: Record<PrintLayout, number> = {
  "2x3": 2/3, "4x6": 2/3, square: 1, "2x6strip": 2/6,
};
```

`computeCoverCropRect(sourceWidth, sourceHeight, shortToLongRatio, forcePortrait)`:
a "cover" center-crop (fills the target shape completely, never letterboxes).

- **Without `forcePortrait`**: preserves the source's own landscape/portrait
  orientation — compares the source's own short:long ratio against the
  target's; trims whichever dimension is relatively longer.
- **With `forcePortrait`** (used for `"2x3"`/`"4x6"`, whose paper is
  literally fixed-portrait): compares literal `width/height` against
  `shortToLongRatio` directly, NOT the source's own long/short split — a wide
  1920×1080 landscape source still needs its **width** trimmed hard to reach
  2:3 portrait (trimming height there would be wrong). This is a safety net
  independent of §6.5's fix — even if a capture somehow comes back landscape
  anyway, the print crop still forces a portrait shape so there's no
  uncontrolled second crop on Kodak's side.
- **Bottom-anchored height trims**: whenever a crop needs to trim height (on
  either code path), `cropY = sourceHeight - cropHeight` (not centered). The
  caption (`CompositionEngine.compose()`) is always drawn in a strip at the
  very bottom of the photo; a centered height trim could slice straight
  through it even though it looked fine on the un-cropped result screen. This
  was found and fixed as its own bug (see §17) *before* the deeper
  camera-orientation root cause was found.

`cropToPrintLayout(source, layout)` draws that rect into a
`new OffscreenCanvas(rect.width, rect.height)` and returns a new bitmap;
never throws (returns `source` uncropped if no 2D context).

### 7.2 `FaceModel` (`vision/VisionTypes.ts`) — exactly per `CLAUDE.md` section 9

```ts
  leftEye?: Point; rightEye?: Point;
  nose?: Point; mouth?: Point;
  leftEyebrow?: Point; rightEyebrow?: Point;
  faceContour: Point[];
```

### 7.3 Real implementation: `@vladmandic/face-api` in a Web Worker

`vision/FaceDetectionWorker.ts` runs entirely off the main thread
(`CLAUDE.md` section 30/58's "camera -> ImageBitmap -> worker -> detection ->
landmarks" is honored literally).

- **tfjs `cpu` backend, deliberately** — needs no WebGL context/`<canvas>`,
  more reliably available inside a Worker than WebGL-in-worker across
  Safari/iPadOS versions. `wasm` backend is a drop-in swap here if profiling
  on real hardware later shows `cpu` is too slow.
- face-api's environment auto-detection checks for `window`/`document`,
  which don't exist in a Worker; `faceapi.env.setEnv({...})` is called with a
  minimal worker-safe shim: `Canvas: OffscreenCanvas`,
  `CanvasRenderingContext2D: OffscreenCanvasRenderingContext2D`, stub
  `Image`/`Video` classes that just aren't ever constructed, `fetch: self.fetch`.
- `faceapi.tf` (the bundled tfjs-core instance face-api uses internally) is
  cast to `@tensorflow/tfjs-core`'s types purely for compile-time typing;
  using face-api's *own* `tf` instance (not a separately imported one) is
  required for `setBackend`/`ready` to actually affect its computation.
- Model files: `TinyFaceDetectorOptions({ inputSize: 416, scoreThreshold: 0.5 })`
  + `faceLandmark68Net`, both loaded via `loadFromUri(modelBaseUrl)` from
  `public/models/` (bundled — works fully offline). `modelBaseUrl` is
  resolved against `document.baseURI` (`new URL("models/", document.baseURI)`),
  not a bare relative path, so it resolves correctly under a GitHub Pages
  subpath deploy.
- `detectFaces()`: `tf.browser.fromPixels(image)` → `detectAllFaces(...).withFaceLandmarks()`
  → maps each detection through `landmarks68ToFaceModel`. Disposes the
  tensor and closes the input `ImageBitmap` in a `finally`.

`vision/WorkerFaceDetector.ts` is the main-thread handle: spawns
`new Worker(new URL("./FaceDetectionWorker.ts", import.meta.url), {type:"module"})`,
a `postMessage`/`onmessage` request-id protocol (`{id, type: "init"|"detect"}`
→ `{id, type: "ready"|"result"|"error"}`), transfers the `ImageBitmap` into
the worker (`this.send(msg, [image])`). `detect()` never throws — catches and
returns `[]`. A worker-level `onerror` rejects every pending call rather than
hanging forever.

Model init is kicked off once at app startup (`App.tsx`'s
`faceDetector.init().catch(...)`, warning-only) — during booth setup, not
while a guest waits, mirroring `CLAUDE.md` section 2's camera-permission
timing rule.

### 7.4 `landmarks68ToFaceModel` (`vision/Face68LandmarkIndices.ts`)

Pure function, no ML dependency, fully unit-testable. Maps the standard
68-point iBUG/dlib layout:

```
0–16   face contour / jaw outline (index 8 = chin, 0/16 = ear-height ends)
17–21  eyebrow A ("left" in face-api's subject-relative naming)
22–26  eyebrow B ("right")
27–35  nose (bridge + bottom)
36–41  eye A ("left")
42–47  eye B ("right")
48–59  outer lips
60–67  inner lips
```

Coordinates are normalized to 0..1 by dividing by image width/height and
clamped. `leftEye`/`rightEye`/`leftEyebrow`/`rightEyebrow`/`nose`/`mouth` are
each a `centroid()` of their landmark range.

## 8. Effects: caricature (mesh warp)

### 8.1 The warp math (`effects/MeshWarp.ts`) — pure, renderer-agnostic

A radial "spherize" around each control point:

```
r' = R * (r/R)^(1/scale)
```

- `scale > 1` → enlarge; `scale < 1` → shrink; `scale === 1` → identity.
- Strictly monotonic in `r` for any positive `scale` ⇒ **the mesh
  mathematically cannot fold over itself**, at any scale magnitude, as long
  as scale stays positive (`safeScale()` floors it at 0.01 defensively). The
  `[0.5, 2.4]` clamp in `Presets.ts` is a *taste* ceiling, not a fold-safety
  requirement.

```ts
export interface ControlPoint {
  center: Point;           // normalized 0..1
  radiusX: number; radiusY: number;  // ellipse of influence
  scale: number;           // 1.0 = no-op
}
```

**Critical fix — "melted face" (§17 history)**: multiple overlapping control
points are composed via **independent-displacement summation**, not
sequential chaining:

```ts
export function warpPoint(point: Point, controlPoints: readonly ControlPoint[]): Point {
  let dx = 0, dy = 0;
  for (const cp of controlPoints) {
    const warped = warpPointSingle(point, cp);
    dx += warped.x - point.x;
    dy += warped.y - point.y;
  }
  return { x: point.x + dx, y: point.y + dy };
}
```

The original version fed each control point's *output* forward as the next
one's input, so overlapping falloff radii (nose/eye/jaw crossing on a turned
face) cascaded into order-dependent, compounding distortion that read as
"melted" rather than cartoonish. Summing independent displacements against
the *original* point removes both the order-dependence and the
cascading-through-already-warped-space effect. Covered by a dedicated
order-independence regression test.

### 8.2 Grid mesh + two renderer tiers

`generateGridMesh(cols, rows)` builds a regular triangulated grid
(`Float32Array` positions doubling as UVs, `Uint16Array` triangle indices).
`warpMeshPositions(mesh, controlPoints)` applies `warpPoint` to every vertex.

- **WebGL2** (`rendering/WebGLRenderer.ts`, `GRID_COLS=48, GRID_ROWS=36`):
  vertex shader IS the entire warp — each vertex uploaded twice (original
  position as `a_uv`, warped position as `a_position`); GPU rasterizes +
  samples; fragment shader is a plain passthrough
  (`rendering/shaders/meshWarp.ts`). **Performance fix (P2, §17)**: context,
  program, VAO, UV buffer, index buffer, and texture object are created
  **once** per `WebGL2MeshWarpRenderer` instance in a lazy `ensureContext()`
  and reused across every `warp()` call; only the warped-position buffer and
  the source texture are re-uploaded per call. The original version
  recompiled both shaders on every single call — real overhead for a
  group photo (up to 6 `warp()` calls per `CLAUDE.md` section 10). Backing
  canvas resizes in place (not recreated) if image size changes between
  calls. `dispose()` releases every cached GL object (a real bug was caught
  writing its own test: the uv/index buffers were originally local variables
  in `ensureContext()`, not instance fields, so `dispose()` leaked them).
- **Canvas2D** (`rendering/CanvasRenderer.ts`, `GRID_COLS=28, GRID_ROWS=20`,
  coarser for speed): no native texture-mapped-triangle primitive, so each
  triangle is drawn individually — clip to the triangle's warped destination
  shape, `setTransform` to the affine map from original→warped, `drawImage`
  the whole source through that clip. `triangleAffineTransform` (solves
  `dst_i = M * src_i` for 3 point-correspondences) is exported and unit
  tested standalone.

`MeshWarpCaricatureEngine` (`effects/CaricatureEngine.ts`) picks WebGL2 if
`WebGL2MeshWarpRenderer.isSupported()`, else Canvas2D, and retries once on
Canvas2D if the primary renderer throws; if *that* also fails, returns the
unmodified image — never crashes (`CLAUDE.md` section 49).

### 8.3 Control-point builders (`MeshWarp.ts`) — per-feature, all wired

All ten are implemented: `buildNoseControlPoint`, `buildEyeControlPoints`,
`buildJawControlPoint`, `buildEarControlPoints`, `buildMouthControlPoint`,
`buildForeheadControlPoint`, `buildCheekControlPoints`,
`buildEyebrowControlPoints`, `buildShoulderControlPoint`,
`buildBodyControlPoint`.

Which have real landmark anchors vs. which are approximated (no dedicated
landmark exists in the 68-point scheme):
- **Real landmarks**: nose (contour centroid), eyes (centroid + interocular-
  distance-derived radius), jaw/chin (contour index 8, radii from
  index 0/16 span), mouth (outer+inner lip centroid), eyebrows (own
  centroid landmarks).
- **Approximated / landmark-anchored**: ears (jaw contour ends 0/16 pushed
  outward — no ear landmarks exist at all), forehead (estimated from the
  gap between eyebrow-centroid and the detector's own bounding-box top —
  no hairline landmarks exist), cheeks (midpoint between eye and jaw contour
  index 2/14), shoulders and body (both anchored below the chin, extending
  down/out — there is no body/segmentation source at all in this build).

`CaricatureConfiguration.faceWidth`/`faceHeight`/`neckScale` are **declared
but never wired to a control point** — they'd need anisotropic (non-radial)
warp support the spherize math doesn't have. Explicit, acknowledged scope cut.

### 8.4 Presets, safety, and per-face variation (`effects/Presets.ts`)

```ts
export const SAFE_MIN_SCALE = 0.5;
export const SAFE_MAX_SCALE = 2.4; // taste ceiling, not fold-safety
```

Nine named presets (`PRESET_CONFIGS`) each set `eyeScale`/`noseScale`/
`jawScale`/`earScale` at minimum (the first four wired features), tuned
toward a **goofy + scary-witch mix**, leaning toward the top of the safe
range by design (explicit user direction: prominent by default, operator
pulls back via `caricatureStrength`).

`"Random"` resolves to `randomWtfConfig(rng)`: forces nose/jaw/ears into a
near-maxed range on every roll (never left to chance), eyes randomly go
either huge or beady, then 2-4 more features from
`[mouthScale, foreheadScale, cheekScale, eyebrowScale, shoulderScale, bodyScale]`
are randomly boosted.

`scaleTowardNeutral(config, strength)`: lerps every `*Scale` field toward 1.0
as `strength` (the operator's `caricatureStrength` setting) drops toward 0.

**Per-face variation** (`varyConfigForFace(base, faceIndex, rng)`) — makes
`CLAUDE.md` section 10's "every face gets its own effect parameters" actually
true (it wasn't, until this was added): every `*Scale` field gets a ±15%
random jitter, and each face's position in a left-to-right-sorted group
(stable ordering, not detector-return order) gets one guaranteed "signature"
feature boosted to a clearly-exaggerated floor, cycling through
`[eyeScale, noseScale, foreheadScale, jawScale, earScale, cheekScale]` — the
literal Person1→giant-eyes / Person2→giant-nose example from the spec.

`CapturePipeline.ts`'s `analyzeAndWarpPhoto` calls `resolvePreset` **once**
per photo, then `varyConfigForFace` once per detected face (sorted
left-to-right) before warping it.

## 12. Printing architecture

### 12.1 Interface (`printing/PrinterAdapter.ts`)

```ts
export interface PhotoPrinter {
  name: string;
  discover(): Promise<PrinterDevice[]>;
  connect(device: PrinterDevice): Promise<void>;
  print(image: Blob | ImageBitmap): Promise<void>;
  cancel(): Promise<void>;
  disconnect(): Promise<void>;
}
```

`PrinterManager` owns the current adapter (swappable via `setAdapter`) and
loops `print()` `copies` times.

### 12.2 Every adapter implemented

- **`MockPrinterAdapter`** — simulated `delayMs` (default 800ms) +
  `failRate`; lets the whole booth flow (including print failure/retry) be
  tested with zero hardware.
- **`BrowserPrintAdapter`** — `window.open(blobUrl)` + `win.print()` on load;
  works anywhere a printer is already registered as a system printer.
- **`AirPrintAdapter`** — thin delegate wrapper around `BrowserPrintAdapter`,
  kept as its own named class purely so operator UI can label it distinctly
  even though the underlying call is currently identical (iPad Safari has no
  direct AirPrint API for web apps — this just routes through the system
  print dialog, which lists any AirPrint printer the iPad already sees).
- **`VendorPrinterAdapter`** — intentionally throws on every method. Per
  `CLAUDE.md` sections 37/62's explicit instruction not to implement a
  vendor-specific bridge until the exact hardware is known/confirmed
  workable — this class exists purely so it's impossible to silently ship a
  no-op vendor integration.
- **`ShareSheetPrinterAdapter`** — **the actual default and actual working
  path**, described in full below.

### 12.3 `ShareSheetPrinterAdapter` — the real Kodak Mini 2 Retro story

This is the single most important printing-architecture fact in the whole
project, and it directly falsifies `CLAUDE.md`'s generic "abstract the
printer, pick an adapter" framing being enough on its own — the actual
hardware constraint had to be *discovered*, not just abstracted around.

**Facts, confirmed via research and then on the real device:**
1. Safari on iOS/iPadOS has **no Web Bluetooth API at all** — not partial,
   none, no WebKit roadmap. No web page can talk to any Bluetooth device from
   this browser, full stop, regardless of the printer's own protocol.
2. The Kodak Mini 2 Retro has **no published SDK or documented protocol** —
   only its own "Kodak Photo Printer" app talks to it. Nothing to
   reverse-engineer into `VendorPrinterAdapter` even if Web Bluetooth existed.
3. The Kodak Photo Printer app is **not a registered iOS share extension**
   — confirmed on the real device: it never appears as a row in
   `navigator.share()`'s sheet, no matter the file/MIME type, and there is no
   way to add it there.
4. The Kodak app is **also not AirPrint-compatible** — so the system print
   dialog can't reach it either.
5. Conclusion: **there is no web-page mechanism of any kind — Web Share API,
   `<a download>`, iframe print, anything — that can hand a photo directly to
   an app that hasn't registered as a share target.** This is a platform
   limitation, not a code bug, and no amount of additional code fixes it.

**The actual working path** (confirmed against what "Save Image" already
does in the same share sheet): save the photo to the Photos library, then
the operator manually opens the Kodak Photo Printer app and picks it from
the camera roll — a real two-tap, two-app hand-off, not a one-tap print.

**The "Print to Kodak" Shortcut improvement**: iOS Shortcuts' Personal
Automations have *no* "photo added to album" trigger at all (checked against
Apple's own trigger list — nothing Photos-related exists), so a background
automation isn't possible. But a Shortcut can be configured to **appear
directly in the share sheet** ("Show in Share Sheet", a real iOS feature).
The operator builds a one-time Shortcut named **"Print to Kodak"** with two
actions — "Save to Photo Album" (targeting e.g. "Halloween 2026") then "Open
App" (targeting Kodak Photo Printer) — with "Show in Share Sheet" on. It then
shows up as its own tappable icon in the same share sheet
`ShareSheetPrinterAdapter` already opens, right next to "Save Image." One tap
does both: saves to the right album *and* launches Kodak automatically. Not
fully zero-tap (Kodak's own in-app Print button still needs one more tap, and
there's no published Kodak Shortcuts action to drive that), but a real
improvement over hunting for the app manually. **This Shortcut is built
entirely in Settings-app/Shortcuts-app configuration on the physical device —
no code can create it.**

```ts
export class ShareSheetPrinterAdapter implements PhotoPrinter {
  name = "Share Sheet (Save Image, then print from the Kodak app)";
  async print(image: Blob | ImageBitmap): Promise<void> {
    const blob = image instanceof Blob ? image : await imageBitmapToBlob(image);
    const file = new File([blob], `ghost-booth-${Date.now()}.jpg`, { type: "image/jpeg" });
    if (!navigator.canShare?.({ files: [file] })) {
      throw new Error("This browser/device can't share image files. ...");
    }
    try {
      await navigator.share({ files: [file] }); // files ONLY — see below
    } catch (err) {
      if (err instanceof DOMException && err.name === "AbortError") return; // not a failure
      throw err;
    }
  }
}
```

**Bug found and fixed: `title`/`text` fields caused a junk extra "image."**
`navigator.share()` originally also passed `title`/`text`. The Web Share API
hands those to the receiver as their own separate shared items, not just
descriptive sheet metadata — the "Print to Kodak" Shortcut's "Receive Images
and 2 more from Share Sheet" step picked up *all* of them, so "Save to Photo
Album" saved the text string as a second, junk "image" right next to the
real photo. Fixed by passing `files: [file]` only, nothing else. (Confirmed
via a test asserting the share call's argument object has *only* a `files`
key.)

`PrintingScreen.tsx`'s copy is adapter-aware: the `shareSheet` adapter's
"success" only ever means "saved to Photos," never "printed" — the copy says
"PHOTO SAVED. If you tapped 'Print to Kodak,' the Kodak app is opening now —
otherwise open it yourself to print." (`browserPrint`/`airPrint`/`mock`
success keeps the original "YOUR PHOTO HAS BEEN CONJURED" line, since for
those adapters success really does mean the print/dialog ran.)

### 12.4 Print layout defaults

`printLayout: "2x3"` (not `CLAUDE.md`'s literal `"4x6"` default) — same 2:3
aspect ratio, matches what the Kodak Mini 2 Retro actually physically outputs.

### 12.5 Operator "TEST PRINTER" tool — made actually useful

Originally printed an empty zero-byte `Blob`. Replaced with
`createPrinterTestBitmap(layout)`: a synthetic 1600×1067 test card (ghost
emoji headline, the configured layout name, a timestamp, a thick orange
border specifically so any stretching/cropping is immediately visually
obvious) run through the exact same `cropToPrintLayout` + `printerManager.print`
path a real photo takes — the fastest way to verify the whole hand-off chain
(share sheet → Kodak app → actual paper) without posing for the camera.

## 13. Composition pipeline

`rendering/CompositionEngine.ts`:

```ts
export interface CompositionConfig { foreground: ImageBitmap; caption?: string; }
export interface CompositionEngine { compose(config: CompositionConfig): Promise<ImageBitmap>; }
```

`Canvas2DCompositionEngine.compose()` is now deliberately minimal: draw
`foreground`, then (if `caption`) draw the caption strip on top. This is
**down from the originally-planned full CLAUDE.md section 28 layer stack**
(background/fog/ghosts/foreground/decorative-effects/caption/frame/branding)
because:
- "My Cameo" ghosts are composited directly onto the foreground bitmap
  *before* it ever reaches this engine (by `OwnerCameoEngine`, in
  `composeSelectedBitmap`), not through a `ghosts` list.
- Frame and Overlays were built, then removed entirely (§10 note).
- Background/fog and date/branding layers were never populated by any
  caller and were removed as dead config surface.

`drawCaption()`: `Impact/"Arial Black"` font at `width * 0.045` px, white
fill with a black stroke outline (`lineWidth = max(2, fontSize*0.08)`),
centered horizontally, anchored at `y = height - fontSize * 1.2` — **always
in a strip at the bottom of the photo**. This bottom placement is exactly
why §6.6's bottom-anchored print crop matters — any centered height crop
risks slicing through this strip.

`drawCaptionOnBitmap(source, caption)` is a standalone utility (own tests)
for drawing just the caption onto an arbitrary bitmap without the rest of
`compose()` — not currently called by the live pipeline (poster-graded
photos get their caption from `compose()`'s own layer like any other photo),
kept for reuse.

### The live composition order (`CapturePipeline.ts`'s `composeSelectedBitmap`)

```
source = selection.goofy ? caricatured : original      (base bitmap pick)
  ↓
ghosted = ownerCameoEngine.composite(source, ghostKey, {opacity})
  ↓
graded  = styleKey ? applyStyle(ghosted, styleKey) : ghosted
  ↓
result  = compositionEngine.compose({ foreground: graded, caption: captioned ? recipe.caption : undefined })
```

Every intermediate bitmap this function allocates fresh (never `source`
itself, which is owned by the long-lived `base` and reused across every
future recompose of this photo) is `.close()`d once the final result is
known — see §17's P0 bitmap-lifecycle fix.

## 14. Rendering tier detection

`rendering/CompositionEngine.ts`'s `detectRenderTier()`:

## 17. Reliability fixes worth preserving verbatim (P0/P1 review round)

A dedicated "reliability review before going live" pass found and fixed
these; all are real, previously-shipped bugs, not hypothetical:

1. **The print-failure screen was unreachable.** `BoothStateMachine` moves
   to `"error"` on `PRINT_FAILED`, but `App.tsx`'s screen router only ever
   checked `boothState === "printing"` for `PrintingScreen`'s failure UI —
   once state flipped to `"error"`, guests hit the generic
   "SOMETHING SPOOKY WENT WRONG" single-button screen instead, directly
   violating `CLAUDE.md` section 39's "never discard the finished image."
   Fixed by routing `"error"` through `PrintingScreen`'s failure branch
   whenever `retryTarget === "printing"`. Also: "TRY AGAIN" previously just
   dispatched `RETRY` with no actual retry behind it; `attemptPrint()` +
   `handleRetryPrint()` fixed that.
2. **`ImageBitmap.close()` was never called anywhere.** Every capture and
   every guest toggle tap allocates full-resolution intermediates. Fixed at
   every allocation site: `analyzeAndWarpPhoto`'s per-face warp loop,
   `composeSelectedBitmap`'s tracked-`fresh`-array cleanup,
   `applyPhotoSelection`'s previous-master cleanup (guarded against aliasing
   `original`/`caricatured`), `handleCountdownComplete`'s stale-photo cleanup
   (deduped via `Set`), and both print/save paths closing their
   `cropToPrintLayout()` output.
3. **Photo Retention / CLEAR TEMP PHOTOS were dead code** — see §15.
4. **Auto Start disabled with a note** — see §16.
5. **No offline/PWA cache existed** despite `CLAUDE.md` section 45's
   requirement — `public/sw.js` was added (§18).
6. **The gh-pages deploy process was fully manual** (hand-typed git-worktree
   dance, repeated 38+ times, no verification the copied `dist/` matched
   `main`) — `.github/workflows/deploy.yml` was added (§19).

Also found and fixed, separately, in roughly this order:
- The "melted face" mesh-warp bug (§8.1).
- WebGL2 renderer recompiling shaders every call (§8.2).
- Business logic living in `App.tsx` instead of testable modules — extracted
  into `CapturePipeline.ts` (`analyzeAndWarpPhoto`/`composeSelectedBitmap`).
- Idle timeout discarding the photo mid-browse — fixed via `activityTick`
  (§20).
- Caption sliced off the *printed* photo while visible on screen — first a
  crop-anchoring bug (§6.6), then the deeper camera-orientation root cause
  (§6.5) that the anchoring fix alone didn't fully solve.
- Stage-sizing CSS bugs on the result screen (vh-based sizing → flex-based
  sizing → `100dvh` fix for iOS Safari's collapsible-chrome viewport quirk).

## 18. PWA / offline

`public/sw.js`, hand-written (no `vite-plugin-pwa` — `CLAUDE.md` section 1's
dependency-avoidance preference), registered from `main.tsx` after first
render (`window.addEventListener("load", ...)`, best-effort, never blocks
startup).

**Deliberately asymmetric caching strategy**, because the project was once
bitten by a stale cached bundle during share-sheet debugging:
- **Navigation requests + `sw.js` itself**: network-first. Online, the
  operator/guest always gets whatever's actually deployed; falls back to
  cache only when the network request fails outright (genuinely offline).
- **Everything else same-origin** (hashed JS/CSS chunks from Vite's
  content-hashed filenames, face-model files, cameo images): cache-first —
  these are either content-hashed or effectively static for a deploy's
  lifetime, so a cache hit is always correct.

`CACHE_VERSION = "ghost-booth-v1"` (bump only on a change to the *worker's
own* caching logic, not on every app deploy — deploys are already handled by
the network-first navigation path). `activate()` deletes every other
`ghost-booth-*` cache key. `CORE_SHELL = ["./", "./manifest.webmanifest",
"./favicon.svg", "./icons.svg"]` is precached on `install`.

`public/manifest.webmanifest`: `display: "standalone"`, `start_url: "."`,
`scope: "."`, one SVG icon (`favicon.svg`, `sizes: "any"`). (Its
`orientation: "landscape"` field is stale — see §16.)

## 19. Deploy pipeline

`.github/workflows/deploy.yml` — GitHub Actions, triggers on push to `main`
(and manual `workflow_dispatch`), `permissions: contents: write`,
`concurrency: group: pages` (no overlapping deploys):

```yaml
runs-on: ubuntu-latest
steps:
  - actions/checkout@v4
  - actions/setup-node@v4 (node 22, npm cache)
  - npm ci
  - npx tsc -b       # type-check
  - npm run lint     # oxlint
  - npm test         # vitest run
  - npm run build    # vite build
  - peaceiris/actions-gh-pages@v4  # publishes ./dist to gh-pages branch
```

Publishes to the **existing `gh-pages` branch** (not GitHub's newer "Deploy
from GitHub Actions" Pages source) specifically so it's a drop-in replacement
for the manual process with **no Pages settings change required**. This
replaced a fully manual git-worktree copy dance (documented in
`PROJECT_LOG.md` as a fallback for one-off debugging, but ordinary deploys
should always go through this workflow now).

## 20. Operator panel & App.tsx orchestration

### 20.1 Access

A plain **tap** on the ghost-emoji booth logo (top-left, `.booth-logo`,
`opacity: 0.5`) opens `OperatorPanel` — not `CLAUDE.md` section 47's
specified 5-second hold (see §16's `HoldToActivate` note).

### 20.2 Every setting exposed (`OperatorPanel.tsx`)

- **Camera**: Flip Auto-Rotation Direction (checkbox, `rotateCaptureCounterClockwise`).
- **Flow**: Countdown seconds (1–10), Auto Start (disabled + note),
  Idle timeout seconds (10–300), Attract Mode (checkbox).
- **Effects**: Caricature Strength (0–1 range), Ghost Strength/opacity (0–1
  range), Preset (select, 10 options), Caption Mode (select: off/random/
  fixed), Fixed Caption (select, only shown when mode is `"fixed"`), My
  Cameo (beta) (checkbox → `ownerCameoMode: "always"|"off"`), Filters
  (fieldset of checkboxes over `STYLE_KEYS` — the merged filter+poster list).
- **Printing**: Printer (select: mock/shareSheet/browserPrint/airPrint),
  Auto Print (checkbox — **not actually wired to anything** that triggers an
  automatic print on result), Copies (1–5), Print Layout (select, 4 options).
- **Misc**: Sound Volume (0–1 range, no playback wired), Photo Retention
  minutes (1–1440), Debug Mode (checkbox — shows `DebugLandmarkOverlay` +
  face count on the result screen).
- **Operator Tools** (button grid): TEST CAMERA, TEST CAPTURE, TEST EFFECT
  (stub alert), TEST PRINTER (real synthetic test card, §12.5), DISCOVER
  PRINTER, CLEAR PRINT QUEUE, CLEAR TEMP PHOTOS (real IndexedDB clear),
  RESET SETTINGS.

### 20.3 App.tsx orchestration & bitmap lifecycle

Module-level singletons (constructed once, reused for the app's whole
lifetime — none hold state worth tearing down between photos):
`printerManager` (starts on `MockPrinterAdapter`, swapped via a `useEffect`
keyed on `settings.printerAdapter`), `caricatureEngine`
(`MeshWarpCaricatureEngine`), `compositionEngine` (`Canvas2DCompositionEngine`),
`ownerCameoEngine` (`OwnerCameoEngine`, built from `CAMEO_FILENAMES`),
`faceDetector` (`WorkerFaceDetector`, model URL resolved against
`document.baseURI`).

Refs (not React state, since they hold `ImageBitmap`s / IDs, not
render-driving values): `cameraRef`, `masterBitmapRef` (the currently
displayed/printable bitmap), `originalBitmapRef`/`caricaturedBitmapRef` (the
two "base" bitmaps — goofy × nothing else; frame/overlay/caption/style are no
longer baked into precomputed variant pairs since the combination space grew
too large to precompute — composing on demand is one cheap canvas draw, well
within toggle-tap latency), `photoRecipeRef` (the per-photo caption, decided
once), `currentPhotoIdRef` (one stable id per capture, for the retention
store).

**Bitmap lifecycle rule, enforced everywhere** (P0 fix, §17): every
`ImageBitmap` allocated by a pipeline stage is `.close()`d the moment it's
superseded, *except* the two long-lived base bitmaps
(`originalBitmapRef`/`caricaturedBitmapRef`, which live for the whole photo)
and whichever bitmap is the current `masterBitmapRef` (still on screen /
about to be printed). Every close site is guarded against accidentally
closing one of those two live bitmaps (reference-equality checks before
calling `.close()`).

**`handleCountdownComplete`** (capture → analyze → default-select):
1. Captures via `captureMasterFrame`.
2. Closes the previous photo's stale bitmaps (deduped `Set`).
3. Calls `analyzeAndWarpPhoto` (detection, per-face warp, caption pick).
4. Sets `photoOptions` from the analysis; resets guest picks to defaults
   (**Goofy on, Ghost off, Caption per `captionMode!=="off"`, Style off** —
   Ghost/Style default off deliberately, so the guest opts into the two
   dramatic whole-photo treatments rather than finding them pre-applied).
5. Calls `applyPhotoSelection` with those defaults to render the first photo.

**`applyPhotoSelection`** (every guest toggle tap funnels through this):
calls `composeSelectedBitmap`, closes the previous `masterBitmapRef` (guarded
against aliasing the base bitmaps), sets the new one as `masterBitmapRef`,
converts to a blob → object URL for the `<img>`, best-effort writes to
`PhotoStore` under `currentPhotoIdRef`, and bumps `activityTick`.

**`activityTick`** — the idle-timeout fix. The idle-timeout `useEffect` was
originally keyed only on `state.booth.state`, but picking a
ghost/filter/caption option never changes booth state (guest stays in
`"result"` the whole time) — so a guest quietly browsing the carousel had the
original capture-time countdown silently expire underneath them, discarding
the photo mid-browse (reported: "photo disappears after ~30 seconds"). Fixed
by bumping a plain counter (`activityTick`) inside `applyPhotoSelection` and
adding it to the idle effect's dependency array, so any guest pick re-arms
the timer. The `"printing"` state is also explicitly excluded from the idle
timer (that transition is printer-driven, not guest-driven, so it should
never race the countdown).

**Retry-print flow**: `attemptPrint()` (shared logic) crops to print layout,
calls `printerManager.print`, dispatches `PRINT_SUCCESS`/`PRINT_FAILED`.
`handlePrintRequested` dispatches `PRINT_REQUESTED` then calls it.
`handleRetryPrint` (wired to `PrintingScreen`'s "TRY AGAIN" on a real
failure) dispatches `RETRY` (state machine: `error` → `retryTarget`, i.e.
`"printing"`) then calls `attemptPrint()` again — genuinely retries, not just
a state flip.

**`handleSavePhoto`** ("SAVE PHOTO" on the failure screen — `CLAUDE.md`
section 39's "never discard the finished image"): crops to print layout,
tries `navigator.share({files:[file]})` (same mechanism as the Kodak
hand-off but invoked directly, independent of the operator's chosen printer
adapter, since this needs to work regardless of *why* printing failed), falls
back to a plain `<a download>` anchor click if sharing isn't available.
`AbortError` (guest backed out of the sheet) is treated as a non-failure.

## 21. Rebuild order (phase-by-phase, reflecting what actually happened / should happen)

This is `CLAUDE.md`'s phase list, corrected to match what was actually built,
in the order it makes sense to build it (not necessarily the exact
chronological order of the real project, which included the ghost-effect
revert and several CSS-layout iterations that a rebuild can skip straight
past).

1. **Shell.** Vite + React + TS project. `BoothStateMachine.ts` (§4) with
   unit tests. `AppState.ts`/`App.tsx` skeleton. Full-screen `AttractScreen`,
   `OperatorPanel` (settings only, no test tools yet), `app.css`'s kiosk
   reset (`100dvh`-aware `.booth-shell` from the start — don't repeat the
   vh-sizing iteration described in §17).

2. **Camera.** `CameraManager` with **portrait** `getUserMedia` constraints
   from the start (§6.1 — don't ship the landscape default and discover the
   bug later). `CameraPreview` (mirrored). `CaptureService.captureMasterFrame`
   including `maybeRotateToPortrait` (§6.5) and the un-mirror step, both from
   day one if the booth's physical mount is known to be portrait. Camera
   error handling (`CameraError` kinds). `CameraScreen` staying mounted
   across camera/ready/countdown/capturing.

3. **Vision.** `FaceDetector` interface + `NullFaceDetector` stub first.
   `VisionTypes.ts`'s `FaceModel`. Then the real
   `WorkerFaceDetector`/`FaceDetectionWorker` using `@vladmandic/face-api` +
   `@tensorflow/tfjs-backend-cpu` (§7.3), with `Face68LandmarkIndices.ts`
   fully unit tested standalone before wiring it into the worker.
   `DebugLandmarkOverlay` + operator Debug Mode toggle, to visually confirm
   detection before building the deformation engine on top of it.

4. **Caricature.** `MeshWarp.ts`'s pure warp math (§8.1) — write the
   independent-displacement-summation version from the start; don't build
   sequential chaining first and discover the "melted face" bug later.
   `generateGridMesh`/`warpMeshPositions`, unit tested. Then, incrementally,
   per `CLAUDE.md`'s own order: nose → eyes → jaw → ears → mouth → forehead
   → cheeks → eyebrows → shoulder → body control-point builders (§8.3), each
   with its own docstring explaining whether it's landmark-real or
   approximated. `Presets.ts` (§8.4) including `varyConfigForFace` from the
   start if multi-person support matters for the event.

5. **GPU rendering.** `WebGL2MeshWarpRenderer` — build the cached-context
   version (`ensureContext()`, reused program/VAO/buffers/texture) from the
   start (§8.2); don't ship the per-call-recompile version. `Canvas2DMeshWarpRenderer`
   fallback with `triangleAffineTransform` unit tested standalone.
   `MeshWarpCaricatureEngine` wiring both tiers with graceful fallback.

6. **Segmentation / per-guest ghost — SKIP.** Per this project's own history,
   don't build `CLAUDE.md` sections 21-23's per-guest segmented ghost echo at
   all unless specifically asked; it was tried, worked, and was rejected on
   taste grounds. Go straight to the ghost-cameo approach instead:

7. **Ghost cameo.** `Cameos.ts` catalog + `OwnerCameoEngine` with **cover-fill
   sizing by default** (§9.2 — not a small corner sticker; that was
   corrected once already). Guest picker via `FeatureCarousel`'s Ghost tab.
   `ghostOpacity` wired to a live-adjustable operator slider from the start.

8. **Filters (merged Horror Filters + Poster tints).** Build `HorrorFilters.ts`
   and `PosterEffect.ts` as two modules, but merge them behind `Styles.ts`'s
   single `StyleKey`/`applyStyle` from the start (§10.3) rather than shipping
   two separate operator sections/guest pickers first. Skip Frame/Overlays
   entirely (§10 note) unless specifically requested.

9. **Composition.** `CompositionEngine.compose()` — foreground → caption only
   (§13); ghost/style are pre-composited onto the source before this stage,
   not through a `ghosts`/`frame` config list. Captions as their own
   guest-facing toggle with reroll-on-tap (§11), not baked-in-always.

10. **Print layout & printing.** `PrintLayout.ts`'s `computeCoverCropRect`
    with `forcePortrait` support and **bottom-anchored height trims** built
    in from the start (§6.6) if the target printer's paper is a fixed
    portrait shape — don't ship the centered-crop version and discover the
    caption-clipping bug later. `PrinterAdapter` interface, `MockPrinterAdapter`
    first (test the whole flow with zero hardware), then research the actual
    target printer's real capabilities (Web Bluetooth support in the target
    browser, AirPrint registration, share-extension registration) **before**
    writing a real adapter — if it turns out to be a Bluetooth consumer
    photo printer with only a vendor app, go straight to a
    `ShareSheetPrinterAdapter` (§12.3) rather than attempting
    `VendorPrinterAdapter`. Document the "Print to Kodak"-style Shortcut
    setup for the operator as an out-of-band device-configuration step, not
    code.

11. **Storage.** `IndexedDB.ts` wrapper, `SettingsStore` (merge-onto-defaults
    pattern from the start, so settings fields can be freely added/removed
    without migrations), `PhotoStore` with retention **actually wired to a
    periodic sweep and to every `applyPhotoSelection` call** from the start
    (§15 — don't ship the dead-code version and fix it later).

12. **PWA/offline.** Hand-written `sw.js` with the asymmetric network-first-
    navigation / cache-first-everything-else strategy (§18) — this can be
    added any time after the app shell exists; not a hard dependency of
    earlier phases.

13. **Reliability pass.** Before calling it done: verify the print-failure
    screen is actually reachable through the real state machine (not just
    the printing state) (§17.1); verify every `ImageBitmap`-allocating
    function closes its own superseded intermediates (§17.2); verify the
    idle timer re-arms on in-place guest interaction, not just booth-state
    changes (§20's `activityTick`); set up CI deploy (§19) instead of a
    manual worktree dance.

14. **Booth mode / auto-detection — not built, and not attempted in this
    project.** If picked up, `CLAUDE.md` section 34's stable-face-detected
    auto-start is the only remaining unbuilt phase from the original spec.
